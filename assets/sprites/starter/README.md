# Starter sprite pack

Generated by `python -m battle_city_tools.assets build`. **Do not edit by hand.**

Every file here is a function of the Blender scene in `assets/blender/` and the packer in
`packages/tools/src/battle_city_tools/assets/`. Editing a pixel or a field by hand makes
the sidecar disagree with the atlas, and `tests/assets` fails on the next run.

| File | What it is |
| --- | --- |
| `atlas.png` | The sheet: 44 frames of 16x16 packed into 128x96, RGBA, binary alpha. |
| `atlas.json` | The versioned sidecar: rectangles, pivots, hitboxes, palette, animations, state mapping, sources, licence, the recorded render settings and the pixel digests. |
| `preview.png` | A labelled contact sheet of every frame, enlarged 3x over a checkerboard. |
| `stage-composite.png` | A stage picture assembled from bundled level `classic-03` and these frames. **Not a game capture** -- see below. |

## Regenerating

Rendering needs Blender; packing and validating do not. The full procedure, the pinned
settings and the recorded environment are in [`../../blender/README.md`](../../blender/README.md).

```sh
uv run --locked --package battle-city-tools python -m battle_city_tools.assets \
    build --frames <render directory> --output assets/sprites/starter
uv run --locked --package battle-city-tools python -m battle_city_tools.assets validate
uv run --locked --package battle-city-tools python -m battle_city_tools.assets describe
```

An ordinary `pytest` or `make ci` run never rewrites these files. It decodes them,
re-derives every claim in `atlas.json` from the pixels, and fails if one does not hold.

## What the sidecar promises

* **Pivots and hitboxes are separate.** `pivot` is where a frame's top left sits relative
  to the entity's anchor, in frame pixels. `hitbox` names a collision box owned by
  `battle_city_sim` -- `tile` 16x16, `tank` 16x16, `projectile` 3x3 -- and the test suite
  asserts those against `battle_city_sim.DEFAULT_RULES`. Art is allowed to be bigger than
  its hitbox: a readable projectile is far larger than the three-pixel square it collides
  with, and that overhang is expressed as a pivot, never as a hitbox change. **Art cannot
  move collision geometry.**
* **Packing is deterministic.** Frames are sorted by name and shelf-packed at a fixed
  width with no padding. The validator re-runs the packer over the declared sizes and
  requires the same rectangles.
* **Integrity is over pixels.** `sha256_pixels` covers the dimensions and the RGBA bytes,
  for the sheet and for every frame. File-byte digests are deliberately absent: the same
  pixels may compress differently on another zlib build. The sidecar does not hash itself.
* **Every opaque pixel is a declared palette colour**, and the palette is the client's
  `theme` palette plus the mid tones a lit render needs.

## Readability without colour

The accessibility and art specifications require a property: the states a player must read
have to survive a viewer who cannot separate two hues. They set no numbers.

The numbers in `atlas.json` under `readability` are this pack's own, and they are
regression guards rather than targets. Each was set by measuring the shipped art and then
writing down a value comfortably underneath it, so a later redraw that flattens a
distinction fails the validator instead of shipping. Specifically, the two factions and
open ground versus forest hold a mean-luma gap; shielded versus unshielded enemies and the
three powerup kinds hold different silhouettes; water phases change shape rather than only
hue; and the two mirror tiles lean in opposite directions, measured as a signed luma
difference between the top-right and top-left quarters of the frame.

Every rule currently passes with margin. The tightest is the player-versus-enemy mean-luma
gap, which measures 25 against a threshold of 18; the mirror lean measures -73 and +68
against a magnitude guard of 10.

Three caveats, because a number in a file invites more confidence than it has earned.
Passing these thresholds is evidence the property holds, not proof of it. It is **not a
conformance claim** against any accessibility standard: there is no contrast ratio here,
no stated viewing condition, and no display assumption. And the pairs are a judgement
about which distinctions a player must make, not an exhaustive derivation from the
specifications -- a mechanical check over grey-scale pixels is a floor under the property,
never a replacement for looking at the art. Changing a threshold is an art decision
recorded in `catalog.py`; lowering one is an admission that a distinction got weaker,
which is the conversation the number exists to force.

## `stage-composite.png` is not a screenshot

It says so across the top of the image, in the image. Nothing that produced it ran the
client, pygame, a window or the simulation: the terrain is the bundled `classic-03`
document read through `battle_city_content`, the sprites are the frames in `atlas.png`,
and the entities are placed by a fixed rule in `composite.py`. It is here because the art
has to be judged at gameplay scale and the only seam that would produce a real capture is
the client's asset library, which the change that produced this pack may not touch. A real
in-game capture arrives when the client reads this atlas.

One thing it shows is easy to misread: an unshielded enemy stands on the first forest cell
and an identical one stands on the open cell beside it. The one under the canopy is
invisible. That is the point -- forest conceals tanks -- and it is why the twin is there.
